## [Unreleased]

### Added
- `profile_table`, the ninth tool: `count(*)` and, for each column asked (the first `MCP_PROFILE_MAX_COLUMNS` that `DESCRIBE` lists by default), `count`, `approx_distinct`, `min` and `max`, by one aggregate query run as the caller through the same read-only guard as `execute_query`, so masks and row filters apply. `mode` is `sample` (the first `MCP_PROFILE_SAMPLE_ROWS` rows, `"scope": "first_rows"`), `bernoulli` (`0 < percent <= 100`, `"scope": "random_sample"`) or `full` (`"scope": "visible_rows"`, within the call's time budget). A type outside a closed list of ordered types gets its count only and `"skipped": ["distinct", "min", "max"]`. `min` and `max` are rendered as the cells of `execute_query`. `--check` prints a `profile_table:` line.
- Context providers (entry point group `akko_mcp_trino.context`, named in `MCP_CONTEXT_PROVIDERS`, none by default): the `akko_mcp_trino.context` package holds the provider interface (`CONTEXT_API = 1`), the types a catalogue's description is made of, the chain that reads the providers in parallel on a dedicated loop behind byte-bounded caches, deadlines, a concurrency bound and breakers, and the statuses an agent sees in place of a provider's error text. `describe_table` and `describe_schema` serve it (see below), and without a provider nothing is started.
- Settings for it, all documented in the README: `MCP_CONTEXT_TIMEOUT_SECONDS`, `MCP_CONTEXT_RESERVE_SECONDS`, `MCP_CONTEXT_MAX_CONCURRENCY`, `MCP_CONTEXT_RETRY_AFTER_SECONDS`, `MCP_CONTEXT_REFUSED_RETRY_SECONDS`, `MCP_CONTEXT_BATCH`, `MCP_CONTEXT_TTL_SECONDS`, `MCP_CONTEXT_CACHE_BYTES`, `MCP_CONTEXT_TERMS_CACHE_BYTES`, `MCP_VISIBILITY_TTL_SECONDS`, `MCP_VISIBILITY_CACHE_BYTES`, `MCP_VISIBILITY_MAX_NAMES`, `MCP_CONTEXT_REQUIRE_SELECT`, `MCP_CONTEXT_CANARY`, `MCP_CONTEXT_TEXT_CHARS`, `MCP_CONTEXT_RESPONSE_CHARS`, `MCP_CONTEXT_MAX_COLUMNS`, `MCP_PROFILE_MAX_COLUMNS`, `MCP_PROFILE_SAMPLE_ROWS`. `MCP_VISIBILITY_ENABLED=false` refuses to start: the filter by Trino's rights cannot be turned off. With a provider loaded, a missing canary and the `service` identity mode are warned of.
- Secrets can be read from a file (a rotation to an empty or undecodable file keeps the last good value and logs a warning; a file replaced by another is read again): `FileSecret` and `secret_setting(env, name)` (`<NAME>_FILE` before `<NAME>`, read again when the file changes) in `akko_mcp_trino.context.secrets`.
- `--check` prints a `context:` line, a `visibility:` line and the lines of each provider; `--check --strict` exits 2 when a provider says it is unreachable (`UNREACHABLE:`). The server sets the `httpx` log to `WARNING` and resets the providers that refused the account on `SIGHUP`.
- Metrics, by provider: `mcp_trino_context_calls_total`, `mcp_trino_context_errors_total` (by status), `mcp_trino_context_call_duration_seconds`, `mcp_trino_context_cache_lookups_total` (hit or miss), `mcp_trino_context_cache_bytes` and `mcp_trino_context_breaker_open`.
- The filter by Trino's rights: `akko_mcp_trino.context.visibility` proves what Trino lists to a caller (`SHOW CATALOGS`, the schemas of a listed catalog, the tables of a listed schema), never with a catalogue's name in a statement, and keeps it per caller (identity mode, subject, roles, catalog) for `MCP_VISIBILITY_TTL_SECONDS` within `MCP_VISIBILITY_CACHE_BYTES`; a failed read is never kept and proves nothing. Its statements carry the client tag `mcp-gate` (`trino_client.GATE_TAG`, `query_tags`, `gate_runner`), on top of an extension's tags.
- The gate on a catalogue's description: `akko_mcp_trino.context.gate` keeps a column only under the exact name Trino lists to the caller, empties a grain with one hidden column, keeps a join only from visible columns to a table and target columns proven visible, and keeps a glossary term, a classification, a tag or a property only when its set is in the allow list, the owner only when it is served. A related term is named only when it is attached to an object proven visible and its glossary is served. Nothing is served from a kind the allow list does not name, nor from a set with an empty name.
- For plugins: `build_server` takes `context_providers` and `register_query_tools` takes `context`, and `context_started` receives the context setup, for whoever must reset or close the chain.
- The `file` context provider (`MCP_CONTEXT_PROVIDERS=file`), the reference for the contract: a JSON file of tables, columns and glossary terms, served only for the sets the operator allows by exact name (`MCP_CONTEXT_FILE`, `MCP_CONTEXT_FILE_GLOSSARIES`, `MCP_CONTEXT_FILE_CLASSIFICATIONS`, `MCP_CONTEXT_FILE_PROPERTIES`, `MCP_CONTEXT_FILE_SERVE_OWNER`; `*` is a name, never a wildcard). The file is read again when it changes (seen within one `MCP_CONTEXT_TTL_SECONDS`), a `values` or `samples` field refuses it (a name may be `values`), and names are written in lower case.
- `akko_mcp_trino.testing`, the contract every context provider passes (install it with `pip install "akko-mcp-trino[contract]"`, the `contract` extra, which brings `pytest>=8,<10`): subclass `ContextContract` and give it a `harness` fixture returning a `ContractHarness` (the factory `build(env, transport)`, the catalogue's recorded answers `replay`, the settings `env`, the `secret` they hold, and the `ContractNames` of the recorded objects). It needs no network, no catalogue and no Trino, and checks that a provider returns the context with its partition columns, leaves out unknown and deleted tables, sends no request for an unmapped catalog, serves nothing outside `served_sets()`, whose sets follow the settings (without its allow lists, it still describes the table and serves no set; the owner, when the provider declares one, is served only when its setting asks for it, and a catalogue with no owner skips that check), returns only the core types, hands back control within its deadline plus `REPLY_MARGIN_SECONDS` (0.5) and leaves no request open, raises `ProviderRefused` on a 401 without sending it again and `ProviderUnavailable` on a timeout, a 503 or a body that is not JSON, keeps its secret, as written, escaped or encoded, out of its logs, `check_lines()` (read again after the catalogue's errors) and exceptions and object names out of its logs and `check_lines()`, imports nothing of the core's Trino side, finds a trap name under its exact name, and folds every name as Trino lists it. A provider without HTTP, such as `file`, skips the checks that need it; the check of `snapshot` comes in 0.8.x. The README has a "Writing a context provider" section.
- `akko_mcp_trino.context` also exports the statuses (`OK`, `NOT_FOUND`, `NOT_MAPPED`, `PARTIAL`, `UNAVAILABLE`, `REFUSED`, `ERROR`, `NOT_CHECKED`), `secret_setting` and `FileSecret`, for adapters. The wheel finds its sub-packages instead of listing them.
- A context provider that fails to load with anything other than a `ValueError` (an import error, a wrong signature) now refuses to start with a message that names the provider and the type of the exception, never its text, and the providers built before it are closed; `--check` prints it as a problem.
- What the tools need from the context: `ContextChain.served_sets(name)` (`None` for a provider that fails to say, which is in `error` for the call and counted, never failing the tool; an empty mapping for one that declares nothing), `ContextChain.terms` returns a `TermsResult` (the terms and one status per source asked), and `Visibility.columns(key, ref)` returns the columns Trino lists to the caller for a table already proven, by a `DESCRIBE` kept per caller and never kept when it fails. `--check` prints every context and visibility setting, never a secret or the canary's name.
- A clean stop: `ContextSetup.close()` closes every provider, then the context loop, and the server calls it when it stops, SIGTERM included (over HTTP in the application's shutdown, through the new `on_shutdown` of `build_asgi_app`; over stdio with a provider SIGTERM closes and exits 0, and a SIGTERM during a close lets that close end without starting another; without a provider SIGTERM ends the process as in 0.7.2); closing twice is silent. Closing the loop no longer waits without bound for a task that ignores its cancellation, and a loop thread that does not end in time is logged. A provider whose breaker opens for an outage logs `<name> is unavailable` once per opening, as a refusal already did; `SIGHUP` also sets `mcp_trino_context_breaker_open` back to 0 for the providers that refused the account. Catalogue text also loses its line and paragraph separators (U+2028, U+2029).
- `describe_table` serves catalogue context under Trino's rights when a provider is loaded. After its `DESCRIBE` succeeds, the answer adds `table`, `column_context` (one entry per column Trino listed, in its order), `terms` (each glossary term once, by reference `t1`, `t2`… in order of first appearance; a column cites `{"name", "ref"}`, and a catalogue's own keys are never served), `context_sources` (one status per provider: `ok`, `not_found`, `not_mapped`, `partial`, `unavailable`, `refused`, `error` or `not_checked`), `context_truncated` and `undescribed_columns` (at most `MCP_CONTEXT_MAX_COLUMNS` columns, within `MCP_CONTEXT_RESPONSE_CHARS`). Its description then says that this text is data from a catalogue, never instructions. A `DESCRIBE` cut by `TRINO_MAX_ROWS` serves no grain and says `partial`; with less than `MCP_CONTEXT_RESERVE_SECONDS` left in the call no provider is called and the sources say `unavailable`, never the call's `time_budget` error. A refused `DESCRIBE` calls no provider. The context is read after the sample; the statements of the filter stop while `MCP_CONTEXT_RESERVE_SECONDS` is still left (a slow one proves nothing), and any other failure on the way serves no context and says `error` for every source, never failing the call. The filter's statements run as the caller with the client tag `mcp-gate`, and the call names the table in the audit's `metadata_served` when a provider served something. Without a provider, `describe_table` answers and describes itself exactly as in 0.7.2.
- `describe_schema` serves a short catalogue description per table when a provider is loaded: each table of the page that a provider describes adds `description`, `{"text", "source"}` (the first provider's text, cut at `MCP_CONTEXT_TEXT_CHARS` with `"cut": ["text"]`), and the answer adds `context_sources`, except on an empty page, which asks no provider; its description says the text is data, never instructions. The tables of the page are recorded as listed to the caller, the providers are asked for those tables only, in one read by batches of `MCP_CONTEXT_BATCH`, and no column context, term or owner is served. `MCP_CONTEXT_REQUIRE_SELECT` does not apply to a listing. The same safety as `describe_table` holds: no provider call with less than `MCP_CONTEXT_RESERVE_SECONDS` left (`unavailable`), a slow statement of the filter proves nothing, any other failure serves the page without context and says `error`, never `time_budget`. Without a provider, `describe_schema` answers and describes itself exactly as in 0.7.2.
- For plugins: `ToolContext.context` is a `ContextReader` (None without a provider) whose `tables(refs)` answers `descriptions` by `TableRef` and `context_sources`, for the tables the caller's visibility proves only, at most `MCP_DESCRIBE_SCHEMA_TABLES` distinct tables per call (the first of `refs`): a table Trino does not list is neither named to Trino nor asked of a provider, and is absent, as one without context; an empty `refs` asks nothing and answers no `context_sources`, as an empty page does. A plugin never receives the chain, the visibility cache nor a provider.
- Catalogue text costs what is served, not what the catalogue sends: `clean_text` reads at most four times its limit (`MCP_CONTEXT_TEXT_CHARS`) of a text and stops at the first character kept past it, and `describe_schema` reads only the description it serves, never another provider's. A name a catalogue gives (a classification, a tag, a set, a property's key, the owner, the tier, a term's name, glossary, status, category or relation, a column of a grain or a join) is read within a window too: one longer than 256 characters once cleaned (`text.NAME_CHARS`, read through `clean_name`) is dropped, never cut, since a cut name is another name, and a term whose name is dropped is not served; a term's name is cleaned once per answer. A property's value is a text, cut at `MCP_CONTEXT_TEXT_CHARS` with `"cut": ["value"]` on that value. A label of a million characters no longer turns `describe_table` into `time_budget`.
- With a context provider, `MCP_CONTEXT_RESERVE_SECONDS` below 0.3 (`config.MIN_CONTEXT_RESERVE_SECONDS`) refuses to start: the chain may wait up to 0.25 s past its deadline for a provider, so a shorter reserve would let the context end past the call's deadline. That end is shared: the terms read after the tables, for the same deadline, get only what is left of it, never a grace of their own.
- `Visibility.selectable` takes `described=True` when the caller's own `DESCRIBE` just listed the columns, which proves the table whatever the cache holds, even with `MCP_VISIBILITY_TTL_SECONDS=0`; a read Trino refuses (`PERMISSION_DENIED`) is kept as refused for `MCP_VISIBILITY_TTL_SECONDS`, any other failure is not kept.
- `GateContract` in `akko_mcp_trino.testing`, the gate proven end to end over a provider: subclass it with a `gate` fixture returning a `GateHarness` (the contract's harness, plus `hidden_table`, `hidden_column` and `hidden_join_target`, objects of the recorded catalogue). It builds the server as it runs, in the `jwt` and `impersonation` identity modes, with `FakeTrino` in place of Trino (`FakeTrino(rights)`, each user's `Visible` tables and columns; every `Statement` recorded with its user, text and client tags), and checks that nothing of a hidden table, column or join target reaches a reply, a `context_sources` status, an audit line, a log line or a metric, that no statement names what Trino had not listed to its caller but the `DESCRIBE` the agent asked of the hidden table, and that a hidden and a missing table get the same from the core (keys, kinds and statuses besides Trino's own error, the audit line besides its error code, the statements). Every check runs against a Trino that answers a hidden object as missing and against one that refuses it (`PERMISSION_DENIED`, `FakeTrino(..., existing=...)`); the leak check reads the replies, the audit lines, the logs and the metrics each on its own; in `jwt` every statement must carry the caller's own token for Trino (`Statement.token`). With `MCP_CONTEXT_REQUIRE_SELECT=true`, a table Trino lists but refuses a read of (`Visible.unreadable`) gets its columns, no context and `not_checked`. A caller who sees everything is served the three objects, so the checks test something. `tests/context/test_gate_contract_file.py` runs it on `file`; importing `akko_mcp_trino.testing` still loads nothing of the core's Trino side.
- The live integration (`integration/run.sh`, run by CI) starts two more servers with the `file` provider (`integration/context.json`, fictitious texts on `tpch.tiny`), one in `jwt` and one in `impersonation` with `MCP_CONTEXT_REQUIRE_SELECT=true`, both with a canary: alice gets the column context, the term and the join of `tpch.tiny.nation`; bob, who sees only `nation` and not its column `comment`, gets nothing of `orders` (from `describe_table`, `describe_schema`, `list_tables` or `search_columns`), of `region` or of that column; without `MCP_CONTEXT_PROVIDERS`, `describe_table` and `describe_schema` answer as in 0.7.2. A third server's canary is a table alice sees: she gets her columns and `not_checked`, and the server logs a WARNING that does not name her. `run.sh` prints Trino's peak memory and its anonymous memory sampled during the checks, and how long the run took; Trino's `mem_limit` is 2304m from that measurement.
- A Helm chart for Kubernetes and OpenShift, in `charts/akko-mcp-trino/` (chart 0.1.0, image 0.7.2): the door on and identity mode `jwt` by default, a non-root pod with a read-only root filesystem that also runs under OpenShift's arbitrary UID, secrets by `secretKeyRef` from an existing Secret, an internal CA, an optional Ingress, OpenShift Route (edge or reencrypt), NetworkPolicy and PodDisruptionBudget, a values schema, render-time refusals of settings the server would refuse (or the door turned off without `auth.acknowledgeNoAuth`), and a `helm test` that calls `/health`, `/ready` and `--check`. CI lints and renders it, validates it with kubeconform (Kubernetes 1.27 to 1.36, the OpenShift Route schema) and runs `ct lint`; `integration/helm/run.sh` is its live proof on a cluster (service and jwt modes), `integration/helm/openshift.sh` on OpenShift.
- `akko-mcp-trino-atlas`, the Apache Atlas context provider, in `providers/atlas/` (Apache 2.0, released with the core under the same number): its package, its entry point `atlas` and the check of its address and authentication (Basic, a Knox token or Kerberos), with answers recorded from Atlas 2.1 and 2.4 and made neutral by `tests/recordings/anonymize.py`. The `atlas` extra installs it with Kerberos (`pip install "akko-mcp-trino[atlas]"`); the container image carries it, inactive unless `MCP_CONTEXT_PROVIDERS` names it. CI runs the core alone and the core with the provider, each package at 100 % coverage, lints `integration/` with the rest, and refuses a dependency under the GPL, the AGPL or the Collate Community License.
- The Atlas provider reads tables: `from_env` returns `AtlasProvider`, which reads the tables Trino lists by batch (`GET /api/atlas/v2/entity/bulk/uniqueAttribute/type/{type}` by `schema.table@<cluster>`, under each type of `ATLAS_TABLE_TYPES`, split under `ATLAS_MAX_QUERY_CHARS`), their columns and partition keys, and serves descriptions always, and glossary term keys, classifications, business metadata and the owner only for the sets `ATLAS_GLOSSARIES`, `ATLAS_CLASSIFICATIONS`, `ATLAS_BUSINESS_METADATA` and `ATLAS_OWNER_ATTRIBUTE` name (empty: none; `*` is a name). `ATLAS_CLUSTERS` is required and its catalogs are folded to lower case; every name returned is folded as Trino lists it, the lower-case spelling winning over another that folds to it. Entities and relations that are not `ACTIVE` are ignored, and a type Atlas does not know yields nothing. The client reads nothing from the environment (`ATLAS_PROXY`, `ATLAS_CA_BUNDLE`, `ATLAS_TIMEOUT_SECONDS`), sends `X-XSRF-HEADER` and its `User-Agent`, keeps the `ATLASSESSIONID` cookie, and tries the next address of `ATLAS_URL` on an outage (a refused connection, a timeout, a body that cannot be decoded, a 5xx). `ATLAS_CONNECT_TIMEOUT_SECONDS` (1 s, below `ATLAS_TIMEOUT_SECONDS`) bounds the opening of a connection, so that a silent or closed address gives way to the next one within the call, and the next calls start at the next address. A redirect is followed only to an address of `ATLAS_URL`, which the next calls then start at (the active server after a passive server's redirect); any other redirect, a 401 or a 403 is a refusal, without another attempt. A 403 with `ATLAS-403-00-001` is not: Atlas refused the account some of the objects asked, the read serves nothing (the whole batch of tables, or that term), the account stays open, and `atlas refused some objects to the account; an account with no read grant serves nothing` is logged once for the call. A 200 that is not JSON (a Knox login page) is unavailable, logged `atlas unreachable` with no address or name. `ATLAS_URL` with a query or a fragment is refused at start. A Knox token is sent as a bearer token. The cluster is sent as `ATLAS_CLUSTERS` writes it, since Atlas matches a qualified name case included. Only Atlas's own "does not exist" answers mean nothing (a 404 with `ATLAS-404-00-009`, a 400 with `ATLAS-400-00-014`); any other 400 or 404 is unavailable. A type Atlas says does not exist is not asked again until `SIGHUP` or a change of the secret's file; when it knows none of `ATLAS_TABLE_TYPES`, the provider logs `atlas knows none of the table types` once. `check_lines()` prints one line per setting (never a secret, a keytab's path or a proxy's address), then asks Atlas its version, with a line that starts with `UNREACHABLE:` when Atlas refuses the account or does not answer, and the table types Atlas does not know.
- The Atlas provider reads glossary terms: `terms()` reads each distinct key once by `GET /api/atlas/v2/glossary/term/{guid}`, the first alone and the rest at most `ATLAS_MAX_CONCURRENT_REQUESTS` at a time (default 4, from 1 to 32), within the call's deadline. A term's glossary is the suffix of its qualified name, and a term outside `ATLAS_GLOSSARIES`, or attached by a qualified name that names no glossary, is never served; its definition is `shortDescription`, else `longDescription`; its status is `additionalAttributes.<ATLAS_TERM_STATUS_ATTRIBUTE>`; its related terms (`synonyms`, `preferredTerms`, `preferredToTerms`, `seeAlso`, `isA`, `replacedBy`) and categories come from the same answer, with no other request, a related term outside the allow list left out. A 404 with `ATLAS-404-00-005` leaves the term out; to any other read it is unavailable, as each read names the "does not exist" codes it accepts.
- The Atlas provider authenticates with Kerberos: `ATLAS_AUTH=kerberos` answers Atlas's `Negotiate` challenge from the keytab of `ATLAS_PRINCIPAL` and `ATLAS_KEYTAB` with `pyspnego` (the `kerberos` extra; without it the server refuses to start), toward `ATLAS_SPN` (default `HTTP@<host of each address>`), with a new context for each negotiation, none while Atlas's session cookie is valid, and again after a redirect of the passive server. The token is SPNEGO (`protocol="negotiate"`). A negotiation the KDC refuses (or a keytab it cannot use) is a refusal of the account, closed for `MCP_CONTEXT_REFUSED_RETRY_SECONDS` as a 401 is, with no other address tried, and `--check` says the account is refused; only a KDC that cannot be found or reached is an outage. `ATLAS_KEYTAB` must be readable at start, and a rotated keytab lifts a refusal. The keytab's path is never printed; `check_lines()` prints the principal. Kerberos is tested against a stand-in for `pyspnego` only, and the Knox token against a fake Atlas only.
- The Atlas provider passes `ContextContract` on answers recorded from Apache Atlas 2.1, the version of reference: a neutral catalogue seeded for every role of the contract and read by an account that may only read (`tests/recordings/atlas-2.1-seed`), and a real catalogue made neutral (`atlas-2.1`), whose missing roles skip their checks with the reason; `GateContract` runs on both too, with no join target, since Atlas has no notion of a join. Apache Atlas 2.4 is a version of compatibility. The README says what the account needs and how to set up SPNEGO; MIGRATING says what changes from the earlier Atlas provider.
- `GateHarness.hidden_join_target` is optional (`None` by default), for a catalogue with no notion of a join: the join scenario then leaves every check of `GateContract`, the new `test_a_hidden_join_target_is_checked_when_the_catalogue_gives_joins` is skipped with the reason, and the contract fails if the provider gives a join for any table it describes ("the provider gives joins: set hidden_join_target"). With a target, that test plays the join scenario alone.
- A context provider may have an optional `reset()` method, named in the `ContextProvider` docstring: `SIGHUP` calls it from the signal handler, so that it forgets what it remembered of its catalogue. It is a plain function that returns `None` at once, sends no request and does not raise; one that raises is logged as `context provider <name>: reset failed (<type>)`, never with its text, and never leaves the signal handler. `ContextContract` checks it when it is defined (`test_a_reset_hook_is_synchronous_quick_and_quiet`, within `RESET_SECONDS`, 0.1 s).

### Changed
- A plugin's describer that raises is no longer silent: `describe_table` still answers its columns and adds `describer_errors`, the number of describers that failed, never their text.

## [0.7.2] - 2026-11-04

The code of 0.7.1, with a shorter description of the reads the allow-list refuses. 0.7.1 is not published on PyPI.

## [0.7.1] - 2026-11-04

A security release that also changes one default: the user is read from `sub`. With Keycloak, set `MCP_JWT_USER_CLAIM=preferred_username` before upgrading, including when you follow the `0.7` image tag. See [MIGRATING.md](MIGRATING.md).

### Security
- Read commands go by an allow-list: `SELECT`, `DESCRIBE` of a table, and `SHOW CATALOGS`, `SHOW SCHEMAS`, `SHOW TABLES`, `SHOW COLUMNS` and `SHOW FUNCTIONS`. Any other command is refused with `kind` `read_only`, including one a later Trino adds. Before, any `SHOW`, `DESCRIBE` and `EXPLAIN` of a read was accepted. Some reads, such as `SHOW STATS` or `EXPLAIN`, can show facts beyond a row filter or a column mask; they are refused by default. `DESCRIBE INPUT` and `DESCRIBE OUTPUT` are refused too.
- A comment before the statement no longer hides its first word: the guard reads it as Trino does. `DESCRIBE` accepts a table name of one to three parts and nothing else (`DESCRIBE FORMATTED`, `DESCRIBE HISTORY`, `DESCRIBE INPUT`, `DESCRIBE OUTPUT` are refused).
- `explain_query` checks a statement without printing its plan: it asks Trino for `EXPLAIN (TYPE VALIDATE)`, as the caller, and answers `{"valid": true}` or the error, with its `kind`, as before.

### Changed
- **The user is read from `sub` by default**, the OpenID Connect standard. Before, the server read `preferred_username`, else `sub`. An identity provider whose `sub` is an opaque id the access rules do not know, such as Keycloak, sets `MCP_JWT_USER_CLAIM=preferred_username` (see MIGRATING.md).

### Fixed
- `execute_query` accepts the reads it refused although its description promised them: `EXCEPT`, `INTERSECT`, `VALUES`, a parenthesized `SELECT`, and a read preceded by a comment. A write or a table function nested in them is still refused.

### Added
- `MCP_EXTRA_READ_COMMANDS` (none by default): the read commands the allow-list refuses, opened one by one by the administrator, comma-separated: `EXPLAIN` (which also brings back the plan in `explain_query`), `SHOW STATS`, `SHOW CREATE`, `SHOW GRANTS`, `SHOW ROLES` (with `SHOW CURRENT ROLES` and `SHOW ROLE GRANTS`), `SHOW SESSION`. Open one only where no row filter or column mask needs to hold. The server says which are open at start, in `--check` and to every MCP host; an unknown name refuses to start. The `system` catalog and `EXPLAIN ANALYZE` stay refused whatever is opened.
- `MCP_JWT_USER_CLAIM` (`sub` by default): the claim of a caller's token that names the user. `sub` is the OpenID Connect standard, the stable and unique identifier the issuer gives the user. A token without it is refused, never read from another claim.
- `MCP_JWT_ALGORITHMS` (`RS256` by default): the signature algorithms a caller's token may use, comma-separated, public-key algorithms only (`RS256`, `RS384`, `RS512`, `PS256`, `PS384`, `PS512`, `ES256`, `ES384`, `ES512`), for an identity provider that signs with RS512 or rotates between two. A shared-secret algorithm (`HS256`...), `none` or an empty list refuses to start.
- For plugins: `akko_mcp_trino.sql_guard.is_read_only_sql` takes `extra_reads`, and `parse_extra_reads(text)` reads the setting.

## [0.7.0] - 2026-11-01

Two discovery tools, paged lists, explained errors. Nothing is removed; one helper for plugins changes its signature. See [MIGRATING.md](MIGRATING.md).

### Added
- Every error a tool answers carries a `kind` that says what to do about it: `syntax`, `column`, `table`, `schema`, `catalog`, `function`, `type`, `permission`, `invalid_argument`, `read_only`, `time_budget`, `unavailable` or `other`. When Trino names the column, table, schema or catalog it could not resolve, the answer also carries `identifier`. A column Trino could not find (`COLUMN_NOT_FOUND`, named) in `execute_query` or `explain_query` adds `hint`, naming the table, or each table, of the agent's own statement the column was written against and advising `describe_table` on it; the name comes from the statement, never from Trino, and only a table the caller sees is named: each candidate, at most four (`MAX_ADVICE_TABLES`), is looked up by equality on each part as written in its catalog's `information_schema.tables`, as the caller, within what is left of the call minus `ADVICE_RESERVE_SECONDS` (2) and at most `ADVICE_LOOKUP_SECONDS` (5), so a slow lookup stops as a plain timeout and never costs the agent its error; a hidden table, a name without schema (a known limit: `FROM accounts` gets no advice), a refusal, an error or less than the reserve left gets no advice. An ambiguous or unnamed column gets no hint, nor does an unqualified column in a statement with a CTE or a subquery, and a statement the parser cannot read gets none, never an error of its own. `unavailable` (an internal error or a lost connection) says the statement is neither valid nor invalid. The `error` message and the audit codes are unchanged.
- `list_catalogs`, `list_schemas` and `list_tables` page their answer: an optional `offset` argument (0 by default) and a `next_offset` key in the answer, the offset of the next page or `null` on the last one. A page holds `TRINO_MAX_ROWS` names, sorted by name. Before, a list longer than the row cap was cut with `truncated: true` and no way to read the rest. `truncated` stays, true exactly when `next_offset` is not `null`. Schemas and tables are paged in Trino, on `information_schema.schemata` and `information_schema.tables` (was `SHOW SCHEMAS` and `SHOW TABLES`). An `offset` that is not a whole number from 0 is refused (`invalid_argument`) before Trino. `list_tables` on a schema that does not exist or that the caller may not see answers `kind` `schema`, "not found or not visible", the same for both, never an empty list for a missing or hidden schema.
- `MCP_MAX_CATALOGS` (10000 by default, 1 at least): `list_catalogs` reads `SHOW CATALOGS` whole, past the row cap, up to this bound (`system` aside), and pages it in the server; above the bound it answers an error, never a cut list. `--check` prints the page size and the bound.
- For plugins: `ToolContext.run` takes `row_limit` (replaces the row cap for a statement the tool builds itself) and `timeout` (lowers one query's time budget, in seconds: the smallest of it, `TRINO_QUERY_TIMEOUT_SECONDS` and what is left of the call wins, and 0 lowers nothing; a query stopped by it raises a plain `TimeoutError` and the call goes on, while one stopped by the call's own deadline raises `CallTimeout`). `ToolContext.run_whole(sql, bound=…, what=…)` reads every row up to a bound, or raises `ValueError`. `ToolContext.page_size` is the row cap. `check_offset(offset)` validates an offset. `TrinoClient.query` takes the same `row_limit` and `timeout`.
- `describe_schema(catalog, schema, offset)`: a schema's tables and views in one call, each with its type, its comment and all its columns (name, type, comment), paged by whole tables in Trino. `MCP_DESCRIBE_SCHEMA_TABLES` (20 by default, from 1 to 100) bounds the tables of a page and `MCP_DESCRIBE_SCHEMA_COLUMNS` (1000 by default) their columns in all; the first table of a page comes whole however wide, and `shortened` says when a page holds fewer tables for the column budget. Comments and columns are read from `system.metadata.table_comments` and `system.jdbc.columns`, which Trino filters for each user; a policy that refuses them gets an error that names what to allow. Each page reads only its own tables' comments and columns, never the whole schema's. A page costs four statements: the schema check, the page of names, one read of the columns bounded by `MCP_DESCRIBE_SCHEMA_COLUMNS` plus one row, which keeps the tables that arrive whole within the budget, and the comments of the tables kept; a first table wider than the budget is read again alone, by its own query, one statement more per `MCP_DESCRIBE_SCHEMA_COLUMNS` columns. A page size above 100 is refused at start. A missing schema and a hidden one answer the same `kind` `schema` error. `--check` prints both bounds.
- `search_columns(text, catalog, schema, cursor)`: the tables and columns that hold every word of a text, ignoring case, in every catalog the caller sees (`system` never), in one catalog or in one schema. A named schema is checked first: one that does not exist and one the caller may not see answer the same `kind` `schema` error, never an empty search said to be complete; a catalog Trino does not know or refuses answers Trino's error. Its description makes it the first tool when the agent does not know where the data lives; the listing tools describe browsing. Whitespace and punctuation split the text into words (`_` belongs to a word), lower-cased one code point at a time as Trino's `lower()` does; a column matches when every word appears in its name, its comment, its table's name or its table's comment, and one word at least in its own name or comment, so a word found only in a table's name never lists all its columns. The answer's `tables` lists, with their comment, the tables whose own name or comment holds every word, which come without their columns (`describe_table` reads them), and the tables that hold a column listed. It reads `system.metadata.table_comments` and `system.jdbc.columns` one schema at a time, in a stable order. A schema costs two statements, its tables then its columns, which read `system.metadata.table_comments` three times and `system.jdbc.columns` twice in all (the tables' statement reads the comments for the tables' own text and again for the columns a table holds; the columns' statement reads both views once); on Hive the comment view is the expensive one, a metastore call per table; every read is filtered by equality on the catalog and the schema, which Trino pushes down to the views. It stays within the call's budget: before each schema it keeps `MCP_SEARCH_RESERVE_SECONDS` (2 by default) in reserve and stops each query in Trino at what is left, so it answers what it searched rather than the call's own error. `tables` and `matches` together stop at the row cap. The answer says what was searched (`schemas_searched`), what was not and why (`not_searched`: `time_budget`, `row_cap` or the `kind` of Trino's error), whether everything in scope was searched over every call of the search (`complete`), and where to resume (`next_cursor`, inside a schema's tables or columns when the row cap stopped it there). When a search of several words is complete and nothing holds every word on any page of its chain of cursors, the same call goes on with a per-word pass: each word alone, by the same rules, scope, row cap, time budget and rights, its rows marked with the `words` that found them, the rows most words found first, and the answer with `partial: true`; one pass reads all the words in two statements per schema, and `complete`, `not_searched`, `schemas_searched` and `next_cursor` (which carries the pass) then speak of it alone, never complete when it could not finish. A page of that pass adds a fixed `hint` for the agent: while it has a `next_cursor`, that the pass is not finished and to call again with it; on its last page, partial matches to pick from, or search again with one word, then `describe_table`; a complete search that found nothing, and the last page of a per-word pass that found nothing, add the other fixed `hint` (one word from a column or table name, never a value, or browse with `list_tables` and `describe_schema`). The description asks for words from column or table names and comments, never a value such as a date, an amount or a code. Each word is one escaped `LIKE` literal, its `_` taken literally; a word shorter than `MCP_SEARCH_MIN_LENGTH` (3 by default) is ignored, a text with no word left is refused and says so, and so is a text of more than `MCP_SEARCH_MAX_WORDS` words (8 by default) or with a word longer than `MCP_SEARCH_MAX_WORD_LENGTH` characters (64 by default), each before Trino is asked anything and with the bound in the message, and a search of every catalog without a call budget. A schema (or a catalog's schema list) slower than `TRINO_QUERY_TIMEOUT_SECONDS` while the call has time left is named `time_budget` and skipped, and so is one slower than a whole call: a call that runs out of time exactly where it resumed, having moved nothing, skips it. Every call advances, so a resumed search never stops at the same place forever. A cursor altered, kept for another search, or naming a catalog the caller does not see is refused (`invalid_argument`); every cursor the server gives resumes, whatever its schema's name. The audit line notes how many tables and columns came and whether the search was cut, never the text. `--check` prints the word bounds and the reserve, refuses a word length below the minimum length, a bound of words below 1, a reserve not below `MCP_CALL_TIMEOUT_SECONDS`, warns of a reserve of 0 with a call budget, and warns that `MCP_CALL_TIMEOUT_SECONDS=0` limits the search to a named catalog.
- For plugins: `ToolContext.visible_catalogs(bound)` lists the catalogs the caller sees, sorted, `system` aside, read whole up to the bound. `ToolContext.schema_visible(catalog, folded, timeout=…)` says whether the caller sees a schema, the same false for a missing and a hidden one; `folded` must already be lower-cased, as the schema names Trino lists are, and the method does not fold it. `akko_mcp_trino.errors.VIEW_REFUSED` names the kinds of an error on a metadata view that its access control can be the cause of.
- For plugins: `akko_mcp_trino.sql_guard.sql_literal(text)` makes a whole Trino string literal; `akko_mcp_trino.errors.metadata_view_error(exc)` explains an error on Trino's metadata views.

### Changed
- The advice on the engine's policy: refuse the `system` catalog **except** reading `system.jdbc` and `system.metadata`, which Trino filters for each user; without them `describe_schema` and `search_columns` answer an error that says so. The agent's SQL stays refused on all of `system`.
- `listing_reply(key, items, next_offset)` takes the next page's offset, or `None`, instead of `truncated`, and answers both keys; a bool is refused with `TypeError`.
- For extension authors: with `TRINO_IDENTITY_MODE=oauth2` over stdio, the guards (`before_auth`, `after_auth`) no longer run once at start. They run on every request that is not discovery, after Trino named the user, so `before_auth` already sees the `principal`, and a binding lasts one request. Discovery (`initialize`, `ping`, the `*/list` methods, notifications) runs no guard. A guard that refuses at start no longer keeps the server from starting and listing its tools: it refuses each call. A refusal, or Trino naming no user, answers the request an `INVALID_REQUEST` error with the guard's reason and its `message`, instead of a bare error.
- `TRINO_IDENTITY_MODE=oauth2` refuses a query without an admitted user, like `jwt` and `impersonation`. Only the identity check, `TrinoClient.current_user()` (`SELECT current_user`), runs before one; it also answers the mode's `ping`.

### Fixed
- The `initialize` result announces the package version (`akko_mcp_trino.__version__`) as the server's version; it was empty, so a client or an audit could not tell which release answered. The server name is unchanged.
- `akko_mcp_trino.sql_guard.safe_sql_string` no longer doubles a backslash: Trino reads no backslash escape in a string literal, so `a\b` became `a\\b`, another value. It still doubles quotes and drops NUL bytes.
- Trino OAuth2 no longer opens the browser when the MCP host starts: startup and discovery never log in, and the login waits for the first request that needs Trino. Every request that is not discovery (a tool call, a resource read, any method a later SDK adds) logs in and is admitted before it runs. Contributed by hk8suva ([#24](https://github.com/AKKO-p/akko-mcp-trino/pull/24)).

## [0.6.0] - 2026-10-17

Safe defaults, and no token passthrough. **Breaking changes**: read
[MIGRATING.md](MIGRATING.md) before upgrading.

### Security
- **No token passthrough.** In `jwt` mode the server no longer sends Trino the caller's own token, which the MCP authorization specification forbids. It obtains a token for Trino by OAuth 2.0 Token Exchange (RFC 8693) at the identity provider, with its own confidential client (`TRINO_TOKEN_EXCHANGE_URL`, `_CLIENT_ID`, `_CLIENT_SECRET`, `_AUDIENCE`, `_SCOPE`, `_VERIFY`), keeps it in memory until shortly before it expires, and never returns it to the agent or the host. The token endpoint is https only.
- **Audience binding (RFC 8707).** A token must be issued for this server: its audience is `MCP_OIDC_AUDIENCE` or the new `MCP_RESOURCE_URL`. A token whose audience includes Trino's (`TRINO_TOKEN_EXCHANGE_AUDIENCE`) is refused, even if it also names this server. A configuration that would accept Trino's audience, or that sets no audience while auth is on, refuses to start.
- **Safe by default.** `TRINO_IDENTITY_MODE` defaults to `jwt` (was `service`); `MCP_AUTH_ENABLED` and `MCP_AUTH_REQUIRED` default to `true` (were `false`). A request without a valid token is refused with `401` and a body that says what to send. `jwt` and `impersonation` refuse to start unless the door requires a valid token. `MCP_AUTH_REQUIRED=true` with `MCP_AUTH_ENABLED=false` refuses to start (it would refuse every request).
- **Service mode only when named, and announced.** `service` mode and an open door are still possible, chosen explicitly. The server then logs a warning at start, `--check` prints it, and every MCP host receives it in the `instructions` of the initialization.
- **Tool annotations follow the settings.** With `TRINO_READ_ONLY=false`, `execute_query` is annotated `readOnlyHint: false`, `destructiveHint: true`, `idempotentHint: false`, its title is "Run a query (writes allowed)" and its description says it may write. Before, it was annotated read-only whatever the setting, so a host could skip a confirmation it should have asked for.
- The README and SECURITY.md say what read-only covers and what it does not: the guard covers what passes through this server, not what a user's Trino rights allow by other means, with the engine rules to make it end to end.

### Added
- Identity mode `impersonation`, for an identity provider without token exchange: the server authenticates to Trino as `TRINO_USER` (password, or a client certificate) and Trino runs each query as the verified caller, under an impersonation rule only that account has. Readiness runs `SELECT 1` as the account, impersonating no one.
- `TRINO_CLIENT_CERT` and `TRINO_CLIENT_KEY`: the server's account may authenticate to Trino by client certificate (mTLS), in `service` and `impersonation` modes.
- `MCP_RESOURCE_URL`: this server's canonical URL. Accepted as an audience; the server publishes its protected resource metadata (RFC 9728) at `/.well-known/oauth-protected-resource` (and under the URL's path), and a `401` carries `WWW-Authenticate: Bearer resource_metadata="…"`. An extension's documents and challenges take precedence.
- `Refusal.message`: a guard may tell the client in the body what to do. `ToolContext.tool(destructive=...)`.
- `Config.problems()` and `Config.warnings()`; `--check` prints `WARNING:` lines.
- `integration/`: a live run against a disposable Keycloak and Trino in Docker (token exchange, impersonation by client certificate, service mode, every refusal at the door), run in CI on every pull request.

### Changed
- Default budgets: `TRINO_QUERY_TIMEOUT_SECONDS` is `60` (was `0`, no limit) and `MCP_CALL_TIMEOUT_SECONDS` is `120` (was `0`). `0` still removes the limit. `TRINO_MAX_ROWS` must be 1 or more, and a negative budget refuses to start.
- `build_server` passes `instructions=` to `mcp_factory` when the configuration has warnings; a custom factory must accept that keyword in `service` mode or with an open door.
- The `serving` log line names the identity mode.

## [0.5.0] - 2026-10-11

First release.

### Added
- Six read-only tools: `list_catalogs`, `list_schemas`, `list_tables`, `describe_table`, `explain_query`, `execute_query`.
- Identity mode `service` (`TRINO_IDENTITY_MODE`, the default): every query runs as `TRINO_USER`, authenticated by `TRINO_PASSWORD` over https when it is set. A password is never sent over http; an unknown mode refuses to start.
- Identity mode `jwt`: the caller's verified bearer is sent to Trino, which verifies it again with its JWT authenticator and runs the query as that user, so Trino's access control decides for each user. https only (refused at start otherwise); a request without a verified bearer is refused, never run as `TRINO_USER`; readiness asks Trino's public `/v1/info`. The bearer is bound at the door only once verified, in a context variable of its own (`akko_mcp_trino.identity.current_bearer`), never in the principal nor the audit line. An extension may subclass `JwtIdentity` and override `trino_token(bearer)` to send Trino another token for the caller.
- Read-only guard on the SQL tree (CTEs and subqueries included), table functions and the `system` catalog refused; row cap with `truncated`, time budget per query and per tool call.
- The door: bearer tokens verified by JWKS (issuer, audience, expiry, clock tolerance), strict mode refusing any request without a verified caller, transports `streamable-http`, `sse` and `stdio`, Host header filter.
- One audit line per call: `request_id`, `tool`, `subject`, `ok`, `error`, `duration_ms`. Queries carry the source (`TRINO_SOURCE`).
- Tool plugins (`akko_mcp_trino.tools`, `MCP_TOOL_PLUGINS`) and extension points (`akko_mcp_trino.extensions`, `MCP_EXTENSIONS`): a package registers a factory `(config, env) -> Extension`. Hooks: `identity_modes`, `audiences`, `before_auth` and `after_auth` guards (`Refusal`, `Admission`), `public_documents`, `challenge`, `routes` (behind the guard), `wrap_audit`, `client_tags`, `describe_table_doc`, `tool_registrars`, `check_lines`. An unknown name, or a factory that cannot serve its settings, refuses to start and is reported by `--check`. An extension can only refuse: its guards run around the core's token verification, never instead of it.
- `ToolContext.add_describer(fn)` and public reply helpers for plugins (`error_reply`, `refusal_reply`, `listing_reply`, `was_cut`).
- `/health`, `/ready`, Prometheus metrics, `--check` and `--version`.
